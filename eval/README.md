# eval

Round-trip evaluation harness used to drive development of this `pdf2docx`
fork: every change to the fork should be validated by re-running the eval and
checking the score table, not just by eyeballing one sample.

## Goal

The output `.docx` must be **easy to edit**, above all else. Concretely: the
user should have to retype/re-enter as little text as possible after
conversion. Visual/layout fidelity to the source PDF (exact pagination,
pixel-perfect rendering) is a secondary concern — some difference in page
count or rendering is acceptable as long as the text content is intact,
correctly reconstructed (real Word paragraphs/lists/tables, not garbled or
dropped text), and editable.

**In short: when a fix trades off `text_sim` against `ssim`/page-count,
prefer the `text_sim` win.** A regression in `text_sim` is bad even if
`ssim` improves; a regression in `ssim`/page-count alone does not block a
fix that improves `text_sim`.

## Layout

```
eval/
  run_eval.py         -- evaluation harness (see "Evaluation" below)
  ISSUES.md            -- running log of known pdf2docx bugs, fixes tried,
                           and current score table; read this before
                           starting work on the fork
  samples/<name>/       -- ground-truth docx fixtures (tracked in git)
    original.docx         -- ground-truth docx the conversion should match
    input.pdf               -- gitignored; PDF to feed the converter (auto-
                              generated from original.docx via LibreOffice
                              and cached here if not provided)
  results/<name>/       -- gitignored; regenerated by every eval run
    output.docx, *.pdf, pages/*.png, diffs/*.png,
    text_diff.txt, text_diff_loose.txt, scores.json
```

This directory is its own `uv` project, depending on the parent `pdf2docx`
checkout via an editable path dependency in `pyproject.toml`:

```toml
[tool.uv.sources]
pdf2docx = { path = "..", editable = true }
```

Because it's an editable install, changes made to the parent `pdf2docx`
checkout take effect immediately — no reinstall needed between edits and
eval runs.

## Setup

Requirements:
- Python >= 3.11
- [`uv`](https://docs.astral.sh/uv/)
- `soffice` (LibreOffice) on `PATH` — used by the eval harness to render
  `.docx` -> `.pdf` for both the visual (SSIM) comparison and to
  auto-generate `input.pdf` from `original.docx` when a sample doesn't ship
  its own PDF.

```bash
cd eval
uv sync --group eval
```

**Gotcha:** if you have another project's virtualenv active in your shell
(`$VIRTUAL_ENV` set), `unset VIRTUAL_ENV` before running any `uv run ...`
command in this directory, otherwise `uv` may resolve dependencies against
the wrong environment. Always run `uv` commands from inside `eval/`, not
from the parent `pdf2docx/`.

## Evaluation (`run_eval.py`)

```bash
uv run run_eval.py
```

Samples are discovered recursively under `samples/` — any directory (at any
nesting depth) containing an `original.docx` is treated as one sample, named
by its path relative to `samples/` (e.g. `vi/unicode/arial`). `results/` and
`samples/**/input.pdf` are gitignored — everything else under `samples/` is
tracked. To add a sample, create `samples/<name>/original.docx` yourself (and
optionally `samples/<name>/input.pdf`).

For each sample, the script:
1. renders `original.docx` -> PDF via LibreOffice (ground truth, and the
   fallback conversion input if `input.pdf` is missing — cached back to disk
   so scores don't drift run-to-run due to LibreOffice's rendering jitter)
2. converts that PDF -> `output.docx` using the local `pdf2docx` fork
3. renders `output.docx` -> PDF via LibreOffice
4. rasterizes every page of both rendered PDFs and scores each pair with
   SSIM
5. diffs `original.docx` vs `output.docx` text content two ways (see
   "Metrics" below)

Results (rendered PDFs, page images, diffs, `scores.json`) are written to
`results/<sample>/` for inspection between iterations.

### Metrics

Each sample produces a row in the printed score table, tracked over time in
`ISSUES.md`:

- **`text_sim` (primary metric)** — whole-document, whitespace/line-break-
  insensitive word-sequence similarity (`difflib.SequenceMatcher` ratio,
  0.0-1.0, higher is better). Computed by concatenating all visible text in
  document order (ignoring paragraph/table-cell boundaries entirely) and
  comparing word sequences. This is what actually matters: a paragraph
  reflowed across a different number of lines, or a heading split across two
  `<w:p>` elements, counts as identical as long as the same words appear in
  the same order — because neither costs the user any retyping. See
  `results/<sample>/text_diff_loose.txt` for a diff showing only real
  content differences (insertions/deletions), with all matching text
  collapsed away.
- **`text_sim_strict` (secondary/diagnostic)** — the same ratio, but computed
  paragraph/table-row level (`extract_text_lines()`): each paragraph and each
  table row is one sequence element. Sensitive to a paragraph being
  split/merged differently even when the words are identical, or a table row
  fragmenting into multiple rows. Useful for spotting *structural* defects,
  but not the metric to optimize for on its own. See
  `results/<sample>/text_diff.txt`.
- **`ssim` / page count (secondary/diagnostic only)** — visual round-trip
  similarity (docx -> LibreOffice -> PDF -> rasterize -> SSIM against the
  original PDF's rendering) and page-count match. Useful for spotting
  rendering bugs (content overflowing a page, broken table borders, a
  section-break gap) but a regression here alone does **not** block a fix —
  only a regression in `text_sim` does.

When evaluating or prioritizing a change to the `pdf2docx` fork, lead with
its effect on `text_sim` (and read `text_diff_loose.txt` for *why* it
changed), not `ssim`.

## Where to look next

`ISSUES.md` is the living record of this project's iteration: the current
score table, every bug found (with root cause, once confirmed), every fix
that landed, and fixes that were tried and reverted (with why, so they
aren't retried blindly). Read it before starting new work on the fork — it
also has a "Suggested next steps" section with the current priority order.
